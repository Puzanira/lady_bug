# Технические детали проекта

Справка для ИИ-агентов (Claude Code и т.п.), которые продолжат работу над
`LadyBugHitTheRoad` — в том числе на другом компьютере, с нуля. Раздел 1 — как
подключиться к проекту агентом. Раздел 2 — как физически устроена разработка
(инструменты, ограничения). Раздел 3 — во что превратилась сама игра
(механики). Раздел 4 — архитектура кода, система за системой.

## 1. Как агенту подключиться к проекту (все варианты)

### Вариант A — MCP-сервер `unity-mcp` (если настроен и работает)
В `~/.claude.json` может быть подключён MCP-сервер:
```json
"unity-mcp": {
  "command": "/Users/<user>/.unity/relay/relay_mac_arm64.app/Contents/MacOS/relay_mac_arm64",
  "args": ["--mcp"]
}
```
Если он поднят и Unity Editor с этим проектом открыт, агенту доступны
инструменты: `Unity_RunCommand`, `Unity_GetConsoleLogs`, `Unity_Camera_Capture`,
`Unity_SceneView_Capture2DScene`, `Unity_SceneView_CaptureMultiAngleSceneView`,
`Unity_AssetGeneration_GenerateAsset`, `Unity_AssetGeneration_GetModels`. Это
потенциально позволяет напрямую видеть консоль/сцену Unity без участия
пользователя.

**Важно:** за всё время разработки этого проекта (десятки итераций правок)
агент **ни разу фактически не использовал** этот MCP-путь — вся работа шла
через Вариант B ниже. Считайте MCP необязательным бонусом, не зависимостью:
если он недоступен, отсутствует в `~/.claude.json`, relay-процесс не
запущен, или инструменты `Unity_*` не появляются в списке — просто
переходите к Варианту B, это штатный, проверенный способ работы.

Как проверить, жив ли MCP: поискать процесс relay (`ps aux | grep relay_mac`)
и/или попробовать вызвать любой `Unity_*`-инструмент. Если не отвечает —
не пытаться чинить/переустанавливать MCP самостоятельно без явной просьбы
пользователя; это внешняя настройка окружения пользователя, а не часть
проекта.

### Вариант B — через файловую систему, без запуска Unity (основной, всегда рабочий)
Пользователь держит Unity Editor открытым на протяжении всей сессии. Из-за
этого агент **не может** сам запускать Unity в `-batchmode` из терминала —
вторая запущенная копия Unity с тем же проектом падает с ошибкой «another
Unity instance is running». Рабочий цикл вместо этого:

1. Агент правит `.cs`-файлы в `UnityProject/Assets/LadyBug/Scripts/` (рантайм-логика)
   и/или `UnityProject/Assets/LadyBug/Editor/SceneSetup.cs` (генератор сцены —
   правится только если меняется состав/расположение объектов на сцене, а не
   только их поведение).
2. Если менялся **только** рантайм-код (`Assets/LadyBug/Scripts/*.cs`, кроме
   `SceneSetup.cs`) — Unity подхватит изменения сама при переключении фокуса
   на Editor (домен перезагрузится, скрипты перекомпилируются). Rebuild
   Scene **не нужен**.
3. Если менялся `SceneSetup.cs` (новые объекты/UI-панели/связи между
   компонентами) — агент обязан попросить пользователя переключиться в
   Unity и выполнить **Tools → Rebuild Scene**. Сам агент этого сделать не
   может — только пользователь, руками, в открытом Editor.
4. Сцена **пересоздаётся с нуля** каждый раз (`BuildScene()` вызывает
   `EditorSceneManager.NewScene(...)` в начале) — она никогда не
   редактируется вручную и не хранится как источник правды. Источник правды —
   код в `SceneSetup.cs`.

Это единственный способ, которым фактически построен весь проект — надёжный
и не требует никакой специальной настройки на новой машине, кроме открытого
Unity Editor у пользователя.

### После правок — как самому проверить, что код не сломан
Агент не может запустить Unity, но может текстово проверить синтаксис:
```bash
python3 -c "
s = open('ПУТЬ/К/Файлу.cs').read()
print(s.count('{')-s.count('}'), s.count('(')-s.count(')'))
"
```
Ноль-ноль не гарантирует компиляцию, но ловит львиную долю опечаток
(незакрытая скобка после большого рефакторинга) до того, как пользователь
увидит ошибку в Unity Console. Практика, которой агент придерживался после
**каждой** правки в этом проекте.

## 2. Инструменты и ограничения разработки

- **`SerializedObject`/`SerializedProperty`** — единственный способ задать
  значения приватных `[SerializeField]`-полей компонентов, создаваемых в
  `SceneSetup.cs` (сам он — Editor-скрипт, лежит в `Assets/LadyBug/Editor/`, не
  попадает в билд). Для `KeyCode`-полей — **обязательно** `.intValue = (int)someKeyCode`,
  не `.enumValueIndex`: порядок объявления констант в `KeyCode` не совпадает
  с их числовым значением, `.enumValueIndex` даст не ту клавишу.
- **`PrefabUtility.SaveAsPrefabAsset`** требует, чтобы любой `Material`,
  на который ссылается объект, был уже сохранён как ассет
  (`AssetDatabase.CreateAsset`) — иначе после сохранения префаба ссылка
  превращается в «битую» (пурпурный материал). Отсюда два похожих хелпера в
  `SceneSetup.cs`: `ApplyColor` (для объектов сцены, не идущих в префаб) и
  `ApplyPersistentColor` (сохраняет материал как ассет — для всего, что
  попадёт в префаб). Игроки и их тени живут прямо в сцене (не в префабах) —
  для них подходит обычный `ApplyColor`/in-memory `Material`.
- **Script execution order через `LateUpdate`** — `SpeedController` считает
  авторазгон/дистанцию/победу в `LateUpdate()`, а не `Update()`, чтобы
  надёжно происходить после всех остальных скриптов кадра без явной
  настройки Script Execution Order (раньше это было существеннее: тут же
  суммировалось голосование газ/тормоз от `PlayerController`/`GestureInput`
  за тот же кадр — газ/тормоз убраны из игры целиком, но метод остался
  `LateUpdate()`, штатно).
- **Регистронезависимая файловая система macOS** — папки `Assets` и `assets`
  на этой машине физически совпадают. Поэтому сырые исходники арта лежат не
  в `assets/`, а в `RawAssets/` (см. структуру репозитория ниже).
- **Отключение компонента останавливает и `OnTriggerEnter`**, не только
  `Update` — используется намеренно: `PlayerController.enabled
  = false` на стартовом экране/во время паузы/помощи одновременно глушит
  и ввод, и обработку столкновений.

### Сборка билда
`UnityProject/Assets/LadyBug/Editor/BuildScript.cs` → `BuildScript.PerformBuild()`
собирает `Assets/LadyBug/Scenes/Main.unity` в `Builds/LadyBugHitTheRoad.app`
(`BuildTarget.StandaloneOSX`). Вызывается через
`Unity -batchmode -quit -executeMethod BuildScript.PerformBuild` — но, как и
с Rebuild Scene, пока Editor открыт у пользователя, агент не может выполнить
это сам.

### Сторонние CLI-инструменты, использованные при подготовке ассетов
- **`swftools`** (`brew install swftools`), команда `swfextract` — вытаскивание
  растровых спрайтов из `RawAssets/swf/LadybugAdventures.swf` (оригинальная
  Flash-игра, источник стиля дороги/препятствий/декораций).
- **`rsvg-convert`** (`brew install librsvg`) — конвертация скачанных SVG в PNG.
- **Wikimedia Commons API** — источник картинок, которых не было в `.swf`
  (конус, колесо, велосипед, животные и т.п.).
- **Генерация картинок через `gpt-image-1-mini`** (`Y-GameLab/yandex_api/gen_asset.sh`)
  — новые прозрачные спрайты (например `CloudWhite1/2.png`, `Sun.png`) вместо
  поиска готовых картинок. Скрипт: `gen_asset.sh "<prompt>" <output.png>
  [size] [background]`, читает OAuth-токен из `~/.eliza_token` (**не
  коммитить, не печатать целиком в вывод** — заведён этой сессией),
  дергает `https://api.eliza.yandex.net/openai/v1/images/generations`
  (внутренний прокси Yandex к OpenAI-совместимому API, платный, но копеечный
  — не связан с внутренним YandexART). Возвращает настоящий RGBA (проверено
  через `PIL`, не просто белый фон) — для чистых спрайтов в промпт стоит явно
  добавлять «no gradient, no drop shadow, no glow, thick clean outline», иначе
  проступает лёгкое виньетирование по краям прозрачности. Сгенерированное
  затем **обрезается по bounding box** (небольшой паддинг) и уменьшается до
  ~400px по большей стороне, чтобы не раздувать репозиторий (см. плотность
  файлов в `Assets/LadyBug/Sprites/` — обычно единицы-десятки КБ на спрайт).

### Git-репозиторий
`lady_bug/` — корень git-репозитория (инициализирован, есть `.gitignore` —
исключает `UnityProject/Library|Logs|UserSettings|Temp` и сгенерированные
IDE-файлы, но **не** `Assets/Prefabs|Materials|Scenes` — они закоммичены как
есть). Remote: **`git@github.com:tony20202021/lady_bug.git`**
(https://github.com/tony20202021/lady_bug), ветка `main`. Push — по SSH,
ключ `~/.ssh/gh/gh` уже прописан в `~/.ssh/config` для `github.com` и
проверен (`ssh -T git@github.com` → аутентифицируется как `tony20202021`).
`gh` (CLI) при этом отдельно **не залогинен** — это отдельная авторизация,
для `git push`/`pull` по SSH она не нужна, нужна только если понадобится
`gh repo create`/`gh pr` и т.п.

### Быстрый старт на новой машине
1. Установить Unity **6000.5.3f1** (или достаточно близкую 6000.x — если
   версии разойдутся, Unity Hub предложит апгрейд `ProjectVersion.txt`, это
   безопасно).
2. Unity Hub → Open → выбрать именно `lady_bug/UnityProject`
   (не `lady_bug/`).
3. После первого открытия: **Tools → Rebuild Scene** — соберёт
   `Assets/LadyBug/Scenes/Main.unity` с нуля из кода. Без этого шага сцены не будет
   вообще (она не хранится в git/файлах вручную).
4. Play.

⚠️ **Частая ошибка — открыть не ту папку.** Если в Unity Hub указать путь к
`lady_bug/` (корню репозитория) вместо `lady_bug/UnityProject/`, Unity увидит
«пустой» проект и **создаст новый бланковый проект прямо там** — свои
`Assets/`, `Library/`, `Packages/`, `ProjectSettings/`, `Temp/`,
`UserSettings/`, поверх репозитория. Симптомы, если это произошло:
- диалог «Opening Project in Non-Matching Editor Installation» с версией,
  которую вы не устанавливали;
- ошибка Package Manager про `com.unity.modules.adaptiveperformance` /
  `com.unity.modules.vectorgraphics` (это дефолтные пакеты нового пустого
  проекта, а не нашего);
- в меню **Tools вообще нет пункта Rebuild Scene** (потому что это не тот
  проект — `SceneSetup.cs` там не существует).

Если так случилось — закрыть Unity, удалить из `lady_bug/` (только из корня,
**не из `UnityProject/`!**) папки `Assets/ Library/ Logs/ Packages/
ProjectSettings/ Temp/ UserSettings/` (проверить `git status`: они попадут
туда как untracked — это и есть признак пустышки), затем в Hub убрать
неправильную запись проекта и открыть заново, указав `UnityProject/`. Уже
случалось дважды за время разработки этого проекта.

## 3. Суть игры

**LadyBugHitTheRoad** — локальный кооперативный (1 или 2 игрока) endless-runner
про божью коровку на дороге с тремя полосами. Игроки делят один мир/дорогу
(не сплит-скрин). Дорога разгоняется **сама, без участия игрока** (раздел
«Скорость и передачи» ниже) — управление ограничено полосой/прыжком/приседом.
Цель: **проехать 100 км** за минимальное время (раздел «Дистанция и цель»);
очки, трюки и максимальная скорость — не критерий победы, а отдельные
накопительные достижения со своими таблицами рекордов (раздел «Рекорды»).

### Стартовый экран (`StartScreenController`)
Дорога стоит, но не мертва: `SpeedController` держит её на фоновой скорости
(`minSpeed`), дорога и боковые декорации едут, спавнер докидывает только
хорошие объекты (`EntitySpawner.PickPrefab` форсирует good, пока игра не
началась) — фон живой. Игроки не реагируют на ввод до подтверждения.

Три строки меню, между ними ↑/↓ (любые: стрелки/WASD), внутри строки ←/→:
1. **1 ИГРОК / 2 ИГРОКА** — превью вживую: второй жук появляется/исчезает,
   в режиме на одного правый жук встаёт на среднюю полосу.
2. **КЛАВИАТУРА / ДАТЧИКИ / ИМИТАТОР** — выбор источника ввода (раздел про
   жесты ниже). «Датчики» (реальное железо) — проверяет
   `GestureSensorSerial.Instance.IsConnected` при старте, запускает игру на
   реальном железе либо показывает «Датчики не найдены» (раздел 5.7);
   «Имитатор» — рабочая клавиатурная симуляция сенсоров.
3. **СТАРТ** — подтверждает клавишей **Space/Enter** (нейтральная клавиша,
   не привязанная ни к одному игроку — раньше был газ I/Shift, но газ как
   действие убран из игры целиком).

Между заголовком и меню — карусель из **10 страниц** (10 сек/страница, по
кругу, `CarouselInterval`): Суть игры → Цель → Управление → 2 схемы трюков
(АРКА, КОЛЬЦО — по одной на экран) → 3 схемы жестов (Присесть/Смещение/
Прыжок-полёт — по одному на экран) → Датчики расстояния (текст) → 4 экрана
топ-результатов (по одному на категорию, с фото — раздел «Рекорды» выше).

Карусель раньше была одним `Text`, у которого просто подменялась строка
(`carouselText`/массив строк `CarouselPages`). Теперь — `carouselPages`
(`GameObject[]`): каждая страница целиком отдельный child-объект того же
размера (1500×200), `StartScreenController.UpdateCarousel` включает ровно
один по индексу `Time.time / CarouselInterval`, остальные выключены —
понадобилось, чтобы часть страниц могла быть не текстом, а настоящей
схемой из UI-примитивов:
- **Схема трюка** (`SceneSetup.CreateTrickDiagramPage`) — заголовок, два
  цветных квадрата (белый = игрок 1/правый, голубой = игрок 2/левый, те же
  тона, что у самих жуков в игре) в позициях по правилу трюка (АРКА — одна
  над другой в одной полосе, КОЛЬЦО — по разные стороны, на разной высоте,
  намекая на «по воздуху»/«понизу»), подпись у каждого квадрата, короткое
  текстовое описание снизу.
- **Схема жеста** (`SceneSetup.CreateGestureDiagramPage`) — заголовок
  (название жеста), 2 «датчика» (`CreateSensorGlyph`: вертикальная красная
  «лазерная» полоса + белый прямоугольник-«ладонь» на её высоте — высоко,
  если рука «вверху», низко — если «внизу», один на руку), крупная стрелка
  Unicode-символом и короткое слово-действие, подпись снизу.
- **Топ-результаты** (`SceneSetup.CreateTopResultsPage` +
  `TopResultsPage.cs`) — см. раздел «Рекорды» выше.

### Управление в игре — клавиатура
- **Правый игрок**: `← →` полоса, `↑` прыжок, `↓` пригнуться.
- **Левый игрок**: `A D` полоса, `W` прыжок, `S` пригнуться.
- **Газа и тормоза больше нет ни в одной схеме управления** (клавиатура,
  датчики, имитатор) — раньше были независимые газ/тормоз на игрока,
  суммировавшиеся в `SpeedController`; теперь дорога разгоняется сама, и
  единственное, что снижает скорость — столкновение с плохим объектом
  (`SpeedController.HalveSpeed`). `PlayerController` лишился полей
  `accelKey`/`brakeKey` и метода `HandleSpeedInput()`.
- **F1** — пауза + экран помощи с полным текстом управления (см. `HelpController`).
- **Выход из игры** — два независимых пути к одному и тому же диалогу
  «Закончить игру?» (`PauseController.OpenDialog()`):
  1. **Q, только пока открыт экран F1** (`HelpController.Update()`
     перехватывает Q и вызывает `OpenDialog()` напрямую) — замена убранного
     «держать тормоз 5 сек»; `PauseController` сам никакого триггера в
     `Update()` не держит, только показывает/обрабатывает диалог по вызову.
  2. **Присесть всем активным игрокам разом на 10 секунд**
     (`DuckToExitController.cs`) — жестовый путь, работающий в любой схеме
     управления (клавиша «вниз» или оба датчика вниз, раз `IsDucking`
     читается через те же обёртки, что и обычный присед). Первые 5 секунд
     — молча; следующие 5 — на экране обратный отсчёт
     (`ВЫХОД ЧЕРЕЗ N`). Отпустить присед в любой момент — сброс таймера в
     ноль. Не считает игроков, деактивированных в режиме на одного
     (`FindObjectsOfType` их не находит).

### Управление в игре — датчики расстояния / имитатор (`GestureInput`)
**2 датчика расстояния на игрока** (по одному над каждой рукой, **бинарные**
— только «близко»/«верх» или «далеко»/«низ», без промежуточной зоны). Кнопки
тормоза на плате/в коде тоже больше нет (раздел 5.7 обновлён отдельно). Два
источника, переключаются в рантайме через `GestureInput.UseRealSensors`:
реальное железо (`GestureSensorSerial`) или клавиатурная заглушка
(`GestureInput.ReadHand()`).

Жесты (переработаны — раньше «обе вверх» статично держать значило прыжок, а
взмах отвечал за газ; теперь газа нет вообще, и сам прыжок стал взмахом):
- **Обе руки вниз** → пригнуться.
- **Одна вверх, другая вниз** → полоса в сторону опущенной руки.
- **Взмах обеими руками разом (ритмично, не статичная поза)** → прыжок-полёт.
  На реальном железе — `GestureInput.FlapTracker`/`RealFlapDetected`
  (несколько переворотов Up/Down подряд за ~1.2 с). В клавиатурном
  имитаторе клавиша **«верх» каждой руки одновременно служит клавишей
  взмаха** — больше нет отдельной 3-й клавиши на руку: держать её даёт
  обычное состояние Up (нужно для диагонального смещения), а **часто
  нажимать** (3 раза за 0.6 с, `RapidPressTracker`, теперь слушает те же
  up-клавиши) даёт взмах → прыжок. Пока взмах активен, `JumpHeld`/`JumpDown`
  гасят сигналы приседа/смещения на этот кадр — иначе дрожание клавиши между
  Up/Neutral во время частых нажатий спамило бы их.

Клавиши имитатора — упрощены с сетки 3×3 (9 клавиш/игрока) до **2×2 (4
клавиши/игрока)**, раз третья («взмах») клавиша на руку больше не нужна:

```
Левый игрок:   Q E          Правый игрок:  U O
               A D                         J L
```
верх лев./прав. руки — Q/E (левый), U/O (правый); низ лев./прав. руки —
A/D (левый), J/L (правый). Оба «низ»-ключа разом = присед; оба «верх»-ключа
разом, часто нажатые = взмах-прыжок. Обратите внимание: `A`/`D` у левого
игрока — те же клавиши, что и клавиатурные полоса влево/вправо для этого же
игрока; конфликта нет, поскольку `PlayerController` в режиме жестов вообще
не читает свои `leftKey`/`rightKey` (переключается на `GestureInput`
целиком), так что повторное использование букв безопасно.

HUD на каждого игрока (снизу вверх): **действие одним словом**
(`GestureActionIndicator` — ПРЫЖОК/ПРИСЕСТЬ/ВЛЕВО/ВПРАВО, без газа/тормоза) →
**сырые числа с датчиков** (`GestureRawValueIndicator` — только мм по рукам,
без тормоза) → **интерпретированные стрелки** (`GestureIndicator` —
рука/✈-значок взмаха/рука) → **сетка сырых нажатий 2×2**
(`GestureKeyIndicator` — квадрат на каждую физическую клавишу, загорается
при нажатии) → **легенда** текстом. В режиме клавиатуры всё тусклое/неактивное
(`GestureInput` не крутит `Update`, пока `enabled == false`).

### Скорость и передачи (`SpeedController`, `SpeedIndicator`, `GearSfx`)
Дорога **всегда разгоняется сама** — не от голосов игроков (тех больше нет),
а по формуле с падающим ускорением: `rate = baseAccel / (1 + CurrentSpeed /
accelFalloffSpeed)`, т.е. чем выше скорость, тем медленнее она продолжает
расти (гиперболическое затухание, качественно читается как «логарифмическое»
из задания — скорость никогда не останавливается и не имеет жёсткого
потолка, кроме страховочного `maxSpeed = 200`). Единственное, что снижает
скорость — столкновение с плохим объектом (`HalveSpeed`, без изменений).
Индикатор скорости — **1 знак после запятой** + номер передачи
(`SpeedController.Gear`, целочисленно, `Gear = floor(CurrentSpeed /
gearStepKmh) + 1`, смена каждые 10 км/ч). Момент смены передачи —
одноразовый звук (`GearShift.mp3`), а внутри передачи звук гула
(`EngineHum.mp3`, зациклен) плавно нарастает по громкости/высоте тона от
низа до верха диапазона передачи и падает обратно сразу после переключения
(`GearSfx.cs`).

### Дистанция и цель (`SpeedController.DistanceKm`, `DistanceIndicator`, `WinSequence`)
`SpeedController` каждый кадр интегрирует свою же скорость в километры
(`DistanceKm += CurrentSpeed * Time.deltaTime / 3600`, км/ч → км/с) и сразу
проверяет `WinSequence.TryTrigger(DistanceKm)` — победа при **100 км**, это
теперь единственное условие конца игры (раньше было 100 очков; счёт заходил
через `ScoreManager.AddScore`, теперь `ScoreManager` только копит число, в
`WinSequence` больше не стучится). Панель «Пройдено X км, осталось Y км»
(`DistanceIndicator`) стоит в общем стеке HUD-панелей под спидометром.

### Рекорды (`HighScoreManager`) — 4 категории, топ-10 каждая
Раньше был один рейтинг (время до победы, с трюками как довеском). Теперь
**4 независимых таблицы топ-10**: время, очки, трюки, максимальная скорость
за забег (`SpeedController.MaxSpeedReached`) — очки/трюки/скорость просто
накапливаются весь забег и фиксируются в момент победы, а не влияют на неё.
Хранение — `PlayerPrefs`, по 10 значений на категорию.
- **Во время игры** панель топ-3 в HUD **циклически показывает по одной
  категории за раз** (`HighScoreManager.UpdateDisplay`, интервал
  `cycleInterval = 5с`, тот же приём с `Time.time`, что и карусель
  стартового экрана).
- **В конце игры** (`WinSequence.RunSequence`) — `HighScoreManager.ReportRun(...)`
  проверяет все 4 категории разом и возвращает список тех, где забег попал
  в топ-10 (плюс `ranksByCategory` — место по **всем** 4 категориям сразу,
  `0` если вне топ-10, для экрана достижений ниже). Если список не пуст —
  `WinSequence.RevealRecords` показывает их **последовательно**, по одной,
  на несколько секунд каждую (`recordRevealDuration = 2.5с`), поверх
  кат-сцены победы.
- **Фото к рекорду** (`PlayerPhotoCapture.cs`) — после каждого показанного
  `RevealRecords`-сообщения, если в системе есть камера
  (`WebCamTexture.devices`), поверх всего экрана запускается: сообщение
  «НОВЫЙ РЕКОРД!»/«N МЕСТО!», «Улыбнитесь — вас снимает камера для
  истории», окно живого превью с камеры (`RawImage`) и обратный отсчёт 5→0
  поверх него; по истечении — кадр из `WebCamTexture.GetPixels()`
  кодируется в PNG и сохраняется в
  `Application.persistentDataPath/PlayerPhotos/`, путь прикрепляется к
  занятому месту (`HighScoreManager.SetPhotoPath(category, rank, path)`) —
  хранится в `PlayerPrefs` как строка, в отдельном параллельном массиве
  `_photoPaths`, который сдвигается синхронно со значениями при вставке
  нового рекорда (`TryInsert`), чтобы фото не «отклеилось» от своего места
  при следующих забегах. Если камеры нет или устройство не стартует за
  `deviceStartTimeout = 3с` (типичный симптом на macOS-билде без
  `NSCameraUsageDescription` в Info.plist — см. предупреждение в самом
  файле) — просто пропускается, без фото.
  **Не проверено на реальном железе/камере** — писалось строго по
  документированному поведению `WebCamTexture`, без возможности запустить
  Unity в этой сессии.
- **Топ-результаты с фото на стартовом экране** (`TopResultsPage.cs`) — 4
  новые страницы в карусели (см. «Стартовый экран» ниже), по одной на
  категорию: топ-3 значений + фото 1-го места, если оно когда-либо было
  прикреплено. Обновляется в `OnEnable()` (при каждом показе страницы), не
  раз при сборке сцены — сами данные существуют только в `PlayerPrefs`,
  на момент `Rebuild Scene` их ещё нет.

### Дорога, препятствия, тени
- 3 полосы. Само полотно дороги статично (не пересоздаётся), но с
  процедурной тайлящейся текстурой асфальтовой «зернистости»
  (`CreateRoadTexture` в `SceneSetup.cs` — Texture2D 64×64, случайный джиттер
  яркости вокруг базового серого, фиксированный seed) — едет через
  скроллинг текстуры (`ScrollingTexture`, тот же приём, что и у разметки).
  Оба скроллера (дорога и разметка) используют `ScrollingTexture`'s
  `dashPeriod`-поле как «мировых единиц на один цикл UV», а не общую
  константу — раньше дорога по ошибке переиспользовала `DashPeriod`
  разметки (4) вместо своего же множителя тайлинга (1.5), из-за чего
  асфальт визуально полз медленнее полос; теперь у обоих один именованный
  источник (`RoadTextureTileSize`), рассинхронизация больше не может
  повториться.
- `EntitySpawner` спавнит объекты в два шага: хороший/плохой, затем (для
  плохого) — перепрыгнуть или пригнуться. Пока `CurrentSpeed <= 0` — не спавнит.
- Хорошие объекты → `+1` к счёту, плохие → `-1` и краш (переворот игрока,
  временная неуязвимость с миганием, скорость дороги падает вдвое — теперь
  единственный способ снизить скорость, раз тормоза нет).
- **Ground-decal препятствия** (`CreateGroundDecalPrefab` в `SceneSetup.cs`,
  массив `GroundDecals`) — Pothole (яма, `Pothole.png`), PuddleBlue (вода,
  `PuddleBlue.png`) и PuddleDark (масляное пятно, `PuddleDark.png`): один
  общий приём, повёрнутый на 90° по X `Quad` с настоящей картинкой, лежащий
  вровень с дорогой. Раньше лужи были 4 цвета (`ProceduralPuddles`) —
  плоские тонированные диски без текстуры, без картинки; теперь только 2
  осмысленных варианта (вода/масло), оба с реальными сгенерированными
  спрайтами, `CreatePuddlePrefab` и её процедурный аналог удалены целиком —
  один `CreateGroundDecalPrefab` обслуживает все 3 (раньше это была
  функция только для ямы, `CreatePotholePrefab`). Перепрыгнуть, не
  пригнуться — все три в пуле `badJumpPrefabs`, без отдельного правила.
- **Кучи мусора** (SandPile/BrickPile/WoodPile/RockPile) — раньше
  собирались из примитивов (`ProceduralPiles`: случайно раскиданные
  кубы/цилиндры/сферы, тонированные цветом материала — не было приличной
  свободной картинки на момент первой версии) — теперь обычные `LaneObjects`
  с настоящими сгенерированными спрайтами (тот же путь, что у любого
  другого стоящего препятствия — `CreateEntityPrefab`), `ProceduralPiles` и
  `CreatePilePrefab` удалены.
- **Shield убран из игры совсем** (был собираемым объектом, +1 к счёту,
  `Shield.png`) — по прямому запросу; вся строка `LaneObjects`, префаб,
  материал и спрайт удалены.
- Арка (`DuckUnderObstacle`) — под ней можно пригнуться, а теперь ещё и
  перепрыгнуть (раньше прыжок был безопасен только если партнёр в этот
  момент приседает в той же полосе — теперь прыжок сам по себе всегда
  безопасен, кооп-трюк «АРКА» просто начисляется бонусом сверху, если
  партнёр действительно приседает рядом). Раньше было 6 цветов через
  тонирование одного бело-серого спрайта (`material.color = archColor`,
  массив `ArchColors`) — по запросу «сделать как на реальных дорогах»
  перегенерирован в один спрайт с **красно-белыми** диагональными полосами
  прямо в текстуре (`SmallArch.png`), тонирование и
  `ArchColors` убраны — `CreateArchPrefab()` больше не принимает цвет,
  всегда один и тот же префаб `"Arch"`.
- **Большая арка на всю дорогу** (`TallArchObstacle`, `CreateBigArchPrefab`/
  `BigArchSpawner.cs`) — инверсия обычной арки: пролёт на все 3 полосы разом,
  проезжается стоя или пригнувшись без проблем, но краш при столкновении в
  воздухе (прыжок/отскок — `PlayerController.IsAirborne`). Тоже спрайт
  теперь, не примитивы: `Assets/Sprites/BigArchSign.png` — сгенерированная
  картинка стальной дорожной П-образной конструкции со знаками и
  светофором (как на настоящих трассах); первая генерация содержала
  нарисованную «дорогу» под аркой (непрозрачные пиксели), которую пришлось
  обрезать по высоте (`.crop`) перед тем как использовать текстуру — иначе
  она перекрывала бы настоящую 3D-дорогу собственным нарисованным куском.
  Спавнится отдельным таймером (`BigArchSpawner`, интервал 9–16 с), не через
  `EntitySpawner` — та рассчитана на выбор одной полосы, а эта арка всегда
  по центру и на всю ширину дороги. Правило пропуска/краша — чисто по
  состоянию игрока (`_verticalState`) в `PlayerController.OnTriggerEnter`,
  не по буквальной геометрии коллайдера — тот же приём, что и у обычной
  арки, и именно поэтому спрайт можно было обрезать без риска сломать
  геймплей: визуал и триггер-коллайдер физически не обязаны совпадать один
  в один.
- **Живые плохие объекты гуляют по полосам** (`LaneWalker.cs`) —
  Dog/Cat/Crow/Rabbit периодически, в случайный
  момент, плавно уезжают вбок в центр соседней полосы (`Mathf.MoveTowards`
  от текущего X к целевому — по пути естественно проходит через край обеих
  полос, поэтому не нужно отдельно кодировать «сначала к краю, потом
  переход»), затем снова ждут случайную паузу и повторяют. `LaneWalker`
  добавляется не всем `LaneObjects`, а только перечисленным в
  `WanderingAnimals` через параметр `canWander` у `CreateEntityPrefab`.
- **Тени** (`GroundShadow`, `AddStaticGroundShadow` в `SceneSetup.cs`): у
  игроков — динамическая тень, всегда строго под ними на уровне дороги
  (X/Z следуют за игроком, Y зафиксирован), помогает рассчитывать прыжки. У
  каждого **плохого** объекта (не у хороших, не у луж/ямы — те и так плоские)
  — статичная тень, запечённая в префаб.

### Небо — облака и солнце
- **Облака** (`CloudDrift.cs`, `CloudSpawner.cs`) — 2 спрайта-варианта
  (`Assets/Sprites/CloudWhite1.png`/`CloudWhite2.png`, сгенерированы через
  `gpt-image-1-mini`, прозрачный PNG, см. раздел «Генерация картинок» ниже),
  спавнятся на случайной высоте/X впереди и медленно плывут на камеру со
  своей **фиксированной** скоростью, не завязанной на `SpeedController` —
  в отличие от `MovingEntity`, продолжают плыть даже на стартовом экране,
  когда дорога стоит на фоновой скорости или игра ещё не начата.
- **Солнце** — один статичный спрайт (`CreateSunSprite` в `SceneSetup.cs`,
  `Assets/Sprites/Sun.png`), без какого-либо компонента движения. Стоит на
  месте, потому что камера в этой игре тоже никогда не двигается (весь эффект
  движения — от объектов, скроллящихся навстречу неподвижной камере) —
  «неподвижное солнце» не потребовало вообще никакой отдельной логики.

### Звук (`SfxManager.cs`, `PlayerMovementSfx.cs`, `GearSfx.cs`)
`GameObject "Audio"` в сцене (создаётся `CreateAudio()` в `SceneSetup.cs`)
держит `SfxManager` (одиночные эффекты, общий `AudioSource.PlayOneShot`) и
`GearSfx` (звук передач — см. «Скорость и передачи» выше). Жужжание
раньше было отдельным вечно-играющим `BuzzController`, привязанным к
скорости дороги — **удалён целиком** (и файл, и вызов из `CreateAudio()`),
потому что задание переопределило, когда именно жужжит жук: теперь это
per-player состояние, не глобальный эмбиент.
- **Бег/полёт игрока** (`PlayerMovementSfx.cs`, по экземпляру на игрока,
  создаётся в `CreatePlayer` → `CreatePlayerMovementSfx`) — 2 зацикленных
  `AudioSource` на игроке (`RunFeet.mp3`/`Buzz.mp3`), оба играют с самого
  начала на громкости 0; каждый кадр компонент **только переключает
  громкость** между ними по `PlayerController.IsAirborne` (бег на земле —
  включая присед, полёт — прыжок/отскок), никогда не вызывает
  `Play()`/`Stop()` заново — так смена состояния не даёт щелчка/рестарта
  посреди цикла.
- **Сбор хорошего объекта** → `SfxManager.PlayPickup()`.
- **Столкновение с плохим объектом** → `SfxManager.PlayBad(entityName)`:
  по имени префаба (`"Dog"`/`"Cat"` с точностью до `(Clone)`-суффикса от
  `Instantiate`) выбирается индивидуальный звук (лай/мяу), для всех
  остальных плохих объектов — общий звук удара (`HitGeneric.mp3`). Хук стоит
  в `PlayerController.OnTriggerEnter`, в обеих ветках: и там, где краш идёт
  через `ScoreValue.value < 0`, и в «запасном» `StartCrash()` в самом конце
  метода (краш без `ScoreValue`, например прыжок в большую арку) — тоже
  получает звук удара.
- **Трюк** (АРКА/КОЛЬЦО, и любой будущий) → `SfxManager.PlayTrick()`, хук в
  одном центральном месте — `TricksManager.SpawnPopup()`, а не в каждом месте,
  где трюк засчитывается, так что новый трюк получает звук бесплатно.
- **Передача** (`GearSfx.cs`) — одноразовый звук смены (`GearShift.mp3`) в
  момент изменения `SpeedController.Gear`, плюс зацикленный гул
  (`EngineHum.mp3`), чья громкость/высота тона плавно растут в пределах
  текущей передачи и падают сразу после переключения — детали в разделе
  «Скорость и передачи» выше.
- Исходники — 9 файлов в `Assets/Audio/*.mp3`, скачаны с mixkit.co (лицензия
  Mixkit — свободное использование, коммерческое и личное, без обязательной
  атрибуции): `Buzz.mp3` (id 1926, «Bee buzz»), `PickupPositive.mp3` (id 2069),
  `BadDog.mp3` (id 1), `BadCat.mp3` (id 93), `HitGeneric.mp3` (id 757),
  `TrickApplause.mp3` (id 482), `RunFeet.mp3` (id 37, «Cartoon insect running
  fast»), `GearShift.mp3` (id 2730, «Motorcycle changing gears»),
  `EngineHum.mp3` (id 2721, «Motorcycle engine working»). Прямые URL вида

  отдаются `WebFetch` (тот видит только кнопку «Download», не сам `<audio>`
  тег) — потребовался прямой `curl` с браузерным `User-Agent` по HTML
  страницы категории и разбор `data-audio-player-preview-url-value`.

### Взаимодействие двух игроков на одной полосе
- Игрок не может сместиться на полосу, где уже **стоит на земле** другой
  игрок. Если целевой (или сам двигающийся) игрок в воздухе (прыжок/отскок)
  — перемещение разрешено, один проходит под/над другим.
- Если игрок прыжком оказывается в одной полосе с игроком на земле, и прыжок
  заканчивается, а тот всё ещё там — приземление не происходит: верхний
  «приземляется» на спину нижнего и тут же автоматически отскакивает снова
  (`Bouncing`-состояние), не долетая до дороги, пока кто-то не покинет полосу.
  Держать «вверх» во время отскока — заряженный прыжок повыше (та же высота,
  что у одиночного прыжка, но от спины партнёра), с таймаутом как у обычного
  прыжка (не виснет бесконечно, даже если клавишу не отпускать).
- Если оба игрока одновременно в воздухе в одной полосе (совпавшие прыжки) —
  побеждает по стабильному приоритету (меньший `GetInstanceID()`), чтобы не
  падали на дорогу вместе.
- **Нижний (несущий) игрок не может прыгнуть, пока на нём кто-то отскакивает**
  (`PlayerController.IsSupportingBouncingPartner()`, проверяется в
  `HandleInput()` перед стартом прыжка) — раньше это было возможным и было
  корневой причиной «игроки иногда сходятся в одно положение»: нижний
  прыгает → перестаёт быть grounded-occupant для верхнего → верхний теряет
  опору и падает на дорогу как раз туда, куда вот-вот приземлится нижний.
  Верхний (`Bouncing`) и так структурно не может пригнуться — в
  `HandleInput()` для состояния `Bouncing` просто нет ветки, читающей клавишу
  приседания.
- **Краш во время отскока сохраняет относительную позицию, а не сбрасывает
  на дорогу.** `StartCrash()` запоминает высоту на момент удара
  (`_crashBaseY`) и было ли состояние `Bouncing` (`_wasBouncingBeforeCrash`);
  `UpdateTumble()` крутит игрока на этой же высоте, а не всегда у земли, и
  по окончании тумбла — если партнёр всё ещё стоит в той же полосе —
  возвращает игрока в `Bouncing` вместо `Normal`. Без этого краш верхнего
  игрока роняет его прямо на дорогу, где уже стоит нижний.

### Трюки (`TricksManager`, `TrickPopup`)
Счётчик — панель по центру справа. Два трюка сейчас:
- **АРКА** — один игрок пригнулся под аркой, другой в этот момент проходит
  над ним по воздуху (прыжок/отскок).
- **КОЛЬЦО** — полный обмен полосами: один игрок пересекает в воздухе, другой
  одновременно проходит понизу, в противоположном направлении.

При засчитывании — всплывающий «+1 ТРЮК: <имя>», летит к счётчику трюков
(мирроринг `ScorePopup`), спавнится в точке события (`ScreenSpaceUtil.WorldToCanvasPoint`),
а не в фиксированной точке экрана.

### Победа
При 100 км (`WinSequence.TryTrigger`, вызывается из
`SpeedController.LateUpdate` при каждом обновлении дистанции) — кат-сцена:
счёт улетает и растёт в центр экрана, объекты гаснут, столкновения
выключаются, ввод глушится, скорость дороги растёт без ограничений, игроки
улетают вдаль, надпись «ВЫ ПОБЕДИЛИ!», затем — если забег попал хоть в одну
из 4 таблиц рекордов — их последовательный показ с фото (раздел «Рекорды»
выше). Время идёт через `GameTimer` (не сырой `Time.time`), с паузами на
стартовом экране/меню помощи/диалоге — не в зачёт.

**Экран достижений** (`WinSequence.CycleAchievements`, `AchievementStats.cs`)
— запускается сразу после показа рекордов (параллельно с остальным, если
что-то ещё доигрывает), крутится **бесконечно** по 4 страницам, каждая
`achievementsPageDuration = 5с` (тот же приём с `WaitForSeconds`-циклом, что
и раскрытие рекордов, только без выхода из цикла — это последнее, что видно
на экране, так что ему не о чем «заканчиваться»): итоги забега (дистанция,
макс. скорость, время), собрано (вишенки/цветы/сердца/всего), сбито
(великосипеды/кошки/собаки/всего), трюки+место по всем 4 категориям сразу
(`RankText` — «#N» или «не в топ-10», раз таблицы хранят только топ-10, а
не полную историю). Числа берутся из **`AchievementStats`** — новый
singleton, копит счётчики по конкретному имени столкнувшегося
объекта/трюка (`RecordCollected`/`RecordHit`/`RecordTrick`, распознаёт по
префиксу имени GameObject'а — `"Cherry"`, `"Bicycle"`/`"Motorbike"`/
`"Motorcycle"` → одна категория «великосипеды» и т.п.), в отличие от
`ScoreManager`/`TricksManager`, которые знают только числовое значение
(+1/-1), не что именно было собрано/сбито. Хуки стоят прямо в
`PlayerController.OnTriggerEnter` (в момент столкновения, не по прилёту
попапа — иначе к моменту чтения `WinSequence` цифры могли ещё «лететь») и
в `TricksManager.SpawnPopup` (тот же центральный хук, что даёт звук
трюка). `HighScoreManager.ReportRun` заодно возвращает `ranksByCategory` —
место по всем 4 категориям, не только по тем, что попали в топ-10.

### Игрок — спрайт и анимация
Спрайт игрока сменился с одной общей картинки (`LadyBug.png`, плоский вид) на
**2 разные картинки**, по одной на игрока (`LadyBug1.png`/`LadyBug2.png`,
`CreatePlayer` получил параметр `spriteFile`, передаваемый в
`CreatePlayerSprite`) — вид с 3/4 ракурса чуть сверху-сзади, будто жук бежит
от камеры вглубь экрана. Обе сгенерированы одним и тем же промптом через
`gpt-image-1-mini` дважды подряд (не 2 разные модели — второй бесплатный
путь, YandexART, отдаёт только JPG без прозрачности, что не годится для
спрайта поверх дороги); генерация не детерминирована, так что 2 вызова с
одним промптом уже дают заметно разные картинки (что и требовалось — «чуть
разный цвет и форма»). У обеих пришлось обрезать нарисованную тень-эллипс
внизу кадра (та же проблема, что у большой арки — модель дорисовывает
контент, который не был явно запрещён, несмотря на промпт «no ground
shadow»).

**Анимация** (`PlayerAnimator.cs`, `LaneWalker.cs`) — целиком процедурная, не
покадровая: независимые генерации от ИИ не гарантируют, что несколько кадров
одного персонажа будут совпадать по стилю/пропорциям/цвету между собой, так
что вместо набора картинок (что просило задание — «4-5 картинок, меняются по
кругу») спрайт просто покачивается по Z-повороту, синхронно с реальным
состоянием:
- Игрок (`PlayerAnimator`) — медленное покачивание на земле (имитация бега
  лапами), более быстрое и мелкое — в воздухе (имитация взмаха крыльями),
  переключается по `PlayerController.IsAirborne`.
- Гуляющие животные (`LaneWalker`, тот же компонент, что и боковое
  перемещение) — лёгкое покачивание на месте, более выраженное — пока
  активно едет в соседнюю полосу (`_moving`), что и есть анимация
  «перемещения», отдельно запрошенная в задании.

## 5. Настоящее железо (Arduino) — установка и что пошло не так

Контекст: `GestureInput.cs` (раздел 4) пока читает клавиатуру-заглушку;
реальные датчики расстояния должны в будущем подключаться через Arduino.
Ниже — что потребовалось, чтобы Arduino IDE вообще заработала на этой
машине, и грабли, на которые агент наступил по пути. Это не про сам
Unity-проект, но следующий агент, продолжающий работу над реальными
датчиками, столкнётся с тем же самым.

### 5.1 Корневая проблема: весь `arduino.cc` недоступен с российского IP
`downloads.arduino.cc` и даже `www.arduino.cc` отдают `403 Forbidden` через
Cloudflare — проверено `curl` (разные User-Agent, не помогает) и напрямую в
браузере (тоже 403) — это гео-блок по IP, не анти-бот защита. Arduino IDE 2
при первом запуске обязательно скачивает `package_index.json`/
`library_index.json` с этого домена — без них зависает на заставке и никогда
не открывает окно. `github.com` при этом **не заблокирован** — это и есть
основа обходного пути ниже.

### 5.2 Текущее решение — рабочий VPN
Установлен **Hiddify** (`/Applications/Hiddify.app`, из стороннего pkg,
ad-hoc подпись). Чтобы у него заработал режим **VPN** (создание TUN-интерфейса),
пришлось решить две отдельные проблемы:

1. **Битая подпись** — `codesign -dv` показывал `Signature=adhoc`,
   `spctl -a -vv` — `invalid Info.plist (plist or signature have been
   modified)`. Причина — у `Contents/Library/LoginItems/
   LaunchAtLoginHelper.app/Contents/Info.plist` были права `600` (только
   root может прочитать) — баг исходной упаковки, не то, что сломал агент
   ранее (хотя agent тоже руками перекладывал `Contents/` при первой
   установке — см. ниже). Почин `codesign` не мог даже прочитать файл
   (`Info.plist=not bound`). Фикс (требует sudo, пароль пользователя):
   ```
   sudo chmod 644 "/Applications/Hiddify.app/Contents/Library/LoginItems/LaunchAtLoginHelper.app/Contents/Info.plist"
   sudo codesign --force --sign - "/Applications/Hiddify.app/Contents/Library/LoginItems/LaunchAtLoginHelper.app"
   sudo codesign --force --deep --sign - "/Applications/Hiddify.app"
   ```
   Это чинит только внутреннюю целостность (ad-hoc остаётся ad-hoc, без
   настоящего Apple Developer ID) — `spctl -a` по-прежнему пишет `rejected`,
   это ожидаемо и не мешает запуску.
2. **Нет привилегированного хелпера для TUN** — даже с починенной подписью,
   режим VPN падал с `manager start inbound/tun[tun-in]: configure tun
   interface: Connect: operation not permitted`. У этой сборки Hiddify нет
   ни `SMJobBless`-хелпера, ни `LaunchDaemon`, ни системного расширения для
   получения прав на `utun` — она просто пытается открыть его напрямую от
   обычного пользователя, а macOS это всегда запрещает без root. Аналог
   того, что на Windows у этого же приложения требовались права
   администратора. **Фикс**: запускать бинарник напрямую через `sudo`, не
   через Dock/Launchpad/Finder (`open` их игнорирует и всё равно стартует
   без прав):
   ```
   sudo "/Applications/Hiddify.app/Contents/MacOS/Hiddify"
   ```
   Держать это окно Терминала открытым, пока нужен VPN. Кнопка
   включения/выключения самого VPN-туннеля внутри приложения дальше
   работает как обычно и не требует повторного `sudo`-перезапуска.

Если что-то из этого не работает у следующего агента/на другой машине —
установочные файлы и PDF-инструкция по CH340-драйверу (раздел 5.4) лежат в
`ArduinoFiles4WorkShop/CH341SER_MAC.ZIP`.

**Проверка, что VPN реально маршрутизирует трафик Arduino IDE** (не
терминала агента — у него, похоже, отдельный network namespace, VPN туда не
пробрасывается): `~/Library/Arduino15/package_index.json` должен быть
~1.6 МБ (официальный, с пакетами `arduino`/`builtin`/... — не самодельная
заглушка), `library_index.json` — ~55 МБ.

### 5.3 Если VPN опять недоступен — офлайн-обход (архив)
До того как VPN заработал, агент вручную собрал рабочий тулчейн в обход
блокировки, полностью через GitHub + Homebrew, без единого запроса к
`arduino.cc`. Весь результат (patch'нутый `platform.txt`, ручное AVR-ядро,
`package_index.json` с зеркалами на GitHub) сохранён — не удалён, а
перенесён в **`Y-GameLab/ArduinoIDE_old_settings/`** (после того как Arduino
IDE и её данные были переустановлены с нуля, см. запрос пользователя «удали
со всеми настройками»). Чтобы восстановить офлайн-путь на новой/той же
машине:

1. Скопировать `ArduinoIDE_old_settings/Documents-Arduino/` →
   `~/Documents/Arduino/` (содержит `hardware/arduino/avr/` — ручное ядро
   платы с патченным `platform.txt`).
2. Скопировать `ArduinoIDE_old_settings/Library-Arduino15/package_index.json`
   → `~/Library/Arduino15/package_index.json` (там прописан пакет `builtin`
   с `serial-discovery`/`mdns-discovery`/`ctags`, скачиваемыми с GitHub
   Releases `arduino/serial-discovery`, `arduino/mdns-discovery`,
   `arduino/ctags`, а не с `arduino.cc`).
3. Убедиться, что стоит Homebrew-тулчейн: `brew install avrdude` (обычный
   `homebrew-core`), `brew tap osx-cross/avr && brew trust --taps
   osx-cross/avr && brew install avr-gcc@9` (сторонний tap, требует явного
   `brew trust` — на этой машине включена такая защита), `brew install
   universal-ctags` (подменяет официальный `ctags`, см. ниже почему).

Собранный этим путём `arduino:avr` (ФQBN `arduino:avr:nano` /
`arduino:avr:uno`) **компилирует и заливает** прошивки нормально — но
**Serial (UART) зависал** на этом пути (см. 5.4, последний пункт) из-за
версии компилятора, а не из-за самого обхода блокировки как такового.

### 5.4 Диагностированные грабли (на будущее)
- **`ctags` из официального релиза Arduino — 32-битный (i386) бинарник 2016
  года**, на современном macOS вообще не запускается (Rosetta переводит
  только x86_64, не i386). Официальный `arduino/ctags` репозиторий на
  GitHub не обновлялся под Apple Silicon. Обход: `brew install
  universal-ctags`, засимлинкать в
  `~/Library/Arduino15/packages/builtin/tools/ctags/<версия-из-package_index.json>/ctags`.
- **`tools.<имя>.path` в `platform.txt` — зарезервированное имя**, которое
  `arduino-cli` всегда подставляет сам (`runtime.tools.<имя>.path`,
  вычисляется из установленного пакета), игнорируя любое ручное значение в
  файле. Из-за этого `{path}` внутри `tools.avrdude.cmd.path={path}/bin/
  avrdude` не резолвился в кастомный Homebrew-путь, а оставался буквальной
  строкой `{runtime.tools.avrdude.path}` — ошибка `cannot execute upload
  tool: fork/exec {runtime.tools.avrdude.path}/bin/avrdude: no such file`.
  Фикс — не пользоваться `{path}`-сокращением вообще, прописывать
  `tools.avrdude.cmd.path`/`tools.avrdude.config.path` **абсолютными
  путями** напрямую (эти конкретные составные имена, в отличие от голого
  `.path`, не зарезервированы и читаются буквально).
- **CH340-клоны и macOS-драйвер**: система сама умеет частично работать с
  CH340 (`/dev/cu.usbserial-N`) без стороннего драйвера, но понадёжнее
  поставить фирменный WCH-драйвер (`CH341SER_MAC.ZIP` из
  `ArduinoFiles4WorkShop/`) — после установки порт переименовывается в
  `/dev/cu.wchusbserial-N`. На современном macOS ставится не как kext, а как
  Driver Extension — требует подтверждения через System Settings → General →
  Login Items & Extensions → Driver Extensions, диалог похож на подтверждение
  сетевого расширения (5.2).
- **Serial зависал (LED замирал на HIGH, ни байта на порту) при сборке
  через Homebrew `avr-gcc@9` (GCC 9.5.0)** — воспроизводилось идентично
  независимо от кабеля, USB-порта, драйвера (системный vs фирменный CH340),
  Arduino `Serial`-библиотеки vs голого доступа к регистрам USART напрямую,
  и отключения watchdog. Чистый GPIO/таймеры (мигание светодиодом без
  Serial) работали идеально в тех же условиях. Плата была полностью
  исправна (чип подлинный `ATMEL MEGA328P`, не клон) — после того как
  заработал VPN и Arduino IDE поставила **официальное** ядро `arduino:avr`
  (штатно собранное под GCC 7.3.0), Serial заработал сразу и стабильно.
  Вывод: расхождение версии `avr-gcc` (9.5.0 из Homebrew vs 7.3.0 у
  официального тулчейна) давало иную генерацию кода для
  прерывание-управляемого UART конкретно — GPIO это не задевало. **Если
  придётся повторно собирать офлайн-путём (5.3) и Serial снова зависнет —
  это тот самый эффект, не аппаратная поломка**; жить с этим (использовать
  датчики без Serial-вывода, например I2C) или попробовать более старую
  версию `avr-gcc` через Homebrew (`avr-gcc@7`, если появится в тапе).

### 5.5 Плата, использованная при отладке
Клон Arduino Nano, USB-C, чип **ATMEL MEGA328P** (подлинный, маркировка
проверена вживую по фото — не LGT8F328P-клон), мост USB-UART — **CH340C**
(отдельная микросхема, VID `0x1A86`, PID `0x7523`).

### 5.6 Референс от преподавателей — набор для мастер-класса
`Y-GameLab/ArduinoFiles4WorkShop/` — офлайн-комплект под 3-платную
архитектуру датчиков, готовую для интеграции с этим проектом:
- `ArduinoSource/PhysInputs`, `Sensors_1`, `Sensors_2` — три готовых скетча
  (кнопка/тач/потенциометр/джойстик/энкодер; фоторезистор/ИК/VL53L0X
  ToF-дальномер/газ-датчик+дыхание; MPU6050 сырыми регистрами
  (clone-friendly, без проверки `WHO_AM_I`) + RFID). Все — **115200 бод**,
  CSV-протокол вида `TOF,<mm>`, `ROT,<x>,<y>,<z>`, и т.п., плюс
  идентификация платы по запросу `?` → `BOARD,<ИМЯ>`.
- `arduino_libs_zip/` — 5 нужных Arduino-библиотек уже скачаны как zip
  (Adafruit VL53L0X/BusIO/Unified Sensor, TM1637Display, MFRC522) —
  ставятся через Sketch → Include Library → Add .ZIP Library, интернет не
  нужен.
- `UnityGrabber/ArduinoSensorsGrabber.cs` — **готовый** `MonoBehaviour` для
  Unity: сам находит все 3 платы по serial-портам (macOS/Windows через
  нативные P/Invoke-обёртки, т.к. Unity не даёт `System.IO.Ports`),
  опознаёт по CSV-рукопожатию, парсит все сенсоры в публичные свойства
  (`TofDistanceValue`, `RotationValue`, `JoystickValue`, и т.п.) — это и
  есть готовая точка интеграции реальных датчиков в `GestureInput.cs`, когда
  до этого дойдёт очередь.

### 5.7 Реализовано: прошивка (4 дальномера + 2 кнопки) + приём в Unity
Решение по архитектуре: **одна плата на обоих игроков**, вместо платы на
игрока. Тормоз в итоге — **не датчик расстояния, а обычная кнопка** (решение
пользователя уже после первой версии прошивки) — поэтому реальных датчиков
расстояния 4 (по руке на каждого игрока), не 6.

**Прошивка** — `ArduinoFirmware/GestureSensors/GestureSensors.ino`. 4×
VL53L0X на одной шине I2C (SDA→A4, SCL→A5) + 2 кнопки на `D6`/`D7`
(`INPUT_PULLUP`, нажата = `LOW`). Раз в ~30 мс шлёт по Serial (115200) одну
CSV-строку:
```
G,<p1_left_mm>,<p1_right_mm>,<p1_brake>,<p2_left_mm>,<p2_right_mm>,<p2_brake>
```
`-1` = нет цели/вне диапазона у дальномера; `<p*_brake>` — `0`/`1`. На `?`
отвечает `BOARD,GESTURE_SENSORS` — опознавательная строка для Unity-стороны.

**Адресация датчиков без пайки.** У конкретных купленных модулей VL53L0X
только 4 пина на разъёме (`VIN/GND/SCL/SDA`) — вывода `XSHUT` на разъёме
нет (обычный способ дать каждому датчику свой I2C-адрес — по очереди
включать их через XSHUT, т.к. все по умолчанию отвечают на одном адресе
`0x29`). Вместо пайки на плату датчика — **`VIN` каждого датчика подключён
не к общей шине питания, а к своему отдельному цифровому пину Nano**
(`D2–D5`): отключение питания достигает того же эффекта, что и XSHUT (датчик
без питания не отвечает на шине), так что прошивка включает их по очереди
через `digitalWrite(pin, HIGH)` и сразу даёт каждому уникальный адрес —
это и есть способ «подключить как есть, без доп. пайки». (~20 мА на
датчик — в пределах того, что может выдать пин ATmega328P.) Важно: адрес
не сохраняется при потере питания — если после `setup()` ещё раз обесточить
пин датчика, при следующем включении адрес придётся присваивать заново
(в `loop()` это не происходит, только один раз при старте).

**Библиотека — не та, что в `ArduinoFiles4WorkShop`!** `Adafruit_VL53L0X`
(та, что использует референсный `Sensors_1.ino` для *одного* датчика) при
нескольких одновременных экземплярах не влезает в 2 КБ RAM ATmega328P —
компилятор явно ругается `data section exceeds available space in board`
(с 6 датчиками нужно было 3444 байта вместо доступных 2048). Заменено на
**Pololu VL53L0X** (`github.com/pololu/vl53l0x-arduino`, MIT, скачана и
установлена как библиотека `~/Documents/Arduino/libraries/VL53L0X/`) —
заметно легче, и умеет `setBus(TwoWire*)` (на случай, если понадобится
переход на программные шины I2C — не потребовалось, т.к. способ с VIN
оказался проще и не требует стороннего кода). С 4 датчиками + 2 кнопками
скетч собирается в 29% флэша / 27% RAM.

**Приём в Unity** — `GestureSensorSerial.cs` (синглтон, шаблон
`Instance`/`Awake()` как у остальных синглтонов проекта, раздел 4). Сам
находит нужный порт (перебирает `/dev/cu.usbserial-*`/`wchusbserial-*`,
посылает `?`, ждёт `BOARD,GESTURE_SENSORS`, чтобы не перепутать с другой
Arduino), читает в фоновом потоке, публикует
`Player1LeftMm`/`Player1RightMm`/`Player1Brake`/`Player2*`. **macOS-only**
(проект и так собирается только под `StandaloneOSX`, см. `BuildScript.cs`) —
свой P/Invoke к termios, без поддержки Windows (в отличие от
`ArduinoSensorsGrabber.cs` из референса, который поддерживает оба, но
рассчитан на три *разных* платы с разными протоколами — здесь протокол один
и простой, обвязка сознательно урезана).

`GestureInput.cs` умеет **оба** источника: `UseRealSensors` (публичное
свойство, не `[SerializeField]` — выставляется в рантайме) переключает
`Update()` между чтением `GestureSensorSerial.Instance` (пороги на
`HandStateForDistance` для рук: `DownThresholdMm = 150`, `UpThresholdMm =
300`, подобраны эмпирически на реальном железе) и клавиатурной заглушкой.
Какая половина каналов достаётся какому игроку — определяется по имени
GameObject'а (`"PlayerRight"` → Player 1), без дополнительной wiring в
`SceneSetup.cs`.

**Важное расхождение с реальной прошивкой после переработки управления
(раздел 3, «убрать газ/тормоз»):** прошивка на плате и `GestureSensorSerial.cs`
**не менялись** — плата физически собрана, кнопки тормоза распаяны и всё ещё
шлют своё состояние по serial (`Player1Brake`/`Player2Brake`), это часть уже
работающего протокола, трогать которую без явной просьбы не стали. Просто
`GestureInput.cs` **больше не читает** эти два поля — тормоз как игровое
действие убран из логики целиком, а не из железа. Если кнопки тормоза когда-то
понадобится физически снять с платы — прошивку придётся поправить отдельно,
но для игры это не требуется: лишние байты в CSV просто игнорируются.
Аналогично, прыжок раньше был статичным жестом «обе руки вверх», теперь —
только взмахом (`RealFlapDetected`, было объединено с бывшим «газом» —
см. `GestureInput.cs` в разделе 4).

**Стартовый экран**: пункт «Датчики» (`_selectedController == 1`) раньше был
заглушкой «не реализовано» — теперь при старте проверяет
`GestureSensorSerial.Instance.IsConnected` и либо запускает игру на реальных
датчиках, либо показывает «Датчики не найдены — проверь подключение платы».

**Проверено на этой сессии, по факту на реальном железе:** обе кнопки
тормоза распаяны и проверены — работают, независимо друг от друга (после
починки: у тактовых кнопок 4 ножки, попарно замкнутые по диагонали — GND и
сигнальный пин должны идти на диагональные, а не соседние с одной стороны,
иначе кнопка «залипает»). Подтверждено и в `Serial Monitor` (сырые CSV),
и в самой игре (реальный тормоз через «Датчики» на стартовом экране реально
тормозит дорогу). Дальномеры (VL53L0X) физически ещё не подключены — VIN-based
адресация проверена только компиляцией, не на реальных датчиках.

### 5.8 Корпус аркадного автомата — концепт-арт (`RawAssets/panel/`)

`RawAssets/panel/` — референсы по физическому корпусу автомата, который
собирается под этот проект (алюминиевый профиль, акриловые панели, отдельно
от Unity-сцены): фото каркаса в процессе сборки, чертёж с размерами
(~1700×900×400 мм — экран наклонён назад как кульман, консоль управления на
уровне пояса, ниша под системный блок снизу), и рукописный эскиз раскладки
органов управления. Эскиз (и его копия `..._with_lights.jpeg` с добавленной
от руки красной/фиолетовой разметкой) описывает на игрока: 2 круглых датчика
расстояния по краям (те же VL53L0X, что и в разделе 5.7) + кнопка «тормоз»
между ними по центру — это и есть та самая, уже распаянная, но не читаемая
игровой логикой кнопка из раздела 5.7/`game-brief.md` («Игровая логика
тормоза с тех пор убрана полностью... кнопки как были распаяны, так и
остались»); аннотация поверх эскиза добавляет кольцо светодиодов по
периметру каждой панели и вертикальный лазерный луч вверх от каждого
датчика расстояния — чисто визуальный эффект для корпуса, не требование к
прошивке/сенсорам.

`RawAssets/panel/generated/concept_full_cabinet_combined.png` — единственный
сохранённый в репозитории концепт-рендер (остальные ~26 промежуточных
вариантов лежат вне репозитория, в `Y-GameLab/.results/panel_concepts/` —
это соседняя папка на уровень выше `lady_bug/`, в отдельный git не входит).
Сгенерирован через `yandex_api/gen_asset.sh`/прямые вызовы Eliza API,
модель **`gemini-2.5-flash-image`** («Nano Banana») — единственная из
опробованных (наравне с `gpt-image-1`, `gpt-image-1-mini` через тот же API),
которая приняла сразу два референса в одном вызове (multi-image
image-to-image: PNG панели + реальный скриншот геймплея
`Screenshot 2026-07-20 at 14.53.03.png`) и правильно скомпоновала их в один
цельный корпус — экран с воссозданным геймплеем сверху, панель управления
без изменений по центру, светящийся ПК-корпус снизу.

Практический вывод по промптингу (пригодится при следующей генерации
подобных многоэлементных сцен): **фронтальный (анфас) ракурс вместо
перспективы 3/4** резко надёжнее для сцен с точным количеством похожих
объектов. В 3/4-перспективе обе модели регулярно путали количество (то
пропадал один из 4 датчиков, то дублировалась кнопка, то элементы двух
игроков сливались в один общий ряд) — не спасали ни редактирование через
`images/edits` (с `mask` в том числе — inpainting поверх готовой картинки
тоже терял/путал элементы при перерисовке), ни явное перечисление «ровно 6
объектов» в тексте. Анфас с пронумерованной раскладкой в промпте (`1 (far
left): ..., 2: ..., 3: ...`) сработал у `gemini-2.5-flash-image` с первой
попытки; `gpt-image-1` тот же анфас продолжал путать даже так — конкретно
для этой задачи (счёт/группировка похожих мелких объектов) Nano Banana
оказалась заметно надёжнее.
